# MNCS Rights & Provenance

A working rights-and-provenance subsystem for the MNCS ecosystem: machine-native
provenance evidence, rights manifests, contribution attestations, release-policy
evaluation, and SPDX interoperability.

> **Status:** experimental implementation, v0.3.0. Not legal advice. Provenance
> records evidence; it does not fabricate legal conclusions, and uncertainty is
> a first-class state throughout the system.

## What actually exists here

| Component | Path | What it is |
|---|---|---|
| Normative policy core | `language/rights_policy.mncs` | The release-policy decision engine written in **MNCS-language** (Profile 0.6). Gate severities, enforcement ceilings, and outcome derivation are defined once here. |
| Normative pressure core | `language/pressure_provenance.mncs` | Tri-state verdicts for distributed pressure (`combine_verdict`, `promotion_combined`, `authority_verdict`, `lineage_verdict`) in **MNCS-language** (module `mncs.rights.pressure.v01`). Returns bare enums so the full corpus runs on `research-bytecode` **and** `portable-wasm` with agreement. |
| Lineage / authority / promotion | `src/mncs_rights_provenance/lineage.py`, `authority.py`, `promotion.py` | ChangeSet lineage records, scoped authority claims (identity ≠ permission), eight independent promotion dimensions (`FAIL > UNKNOWN > PASS`, breakdown retained). |
| Multi-backend corpora | `language/corpora/`, `language/run_backend_tests.sh` | Execution corpora generated from the normative cores; run on `research-bytecode` and `portable-wasm` backends with cross-backend agreement checks. |
| Golden vectors | `conformance/golden-vectors.json`, `conformance/pressure-golden-vectors.json` | Cross-implementation contracts consumed by Python tests and (for policy) `mncs-validator-rs`. |
| Reference library | `src/mncs_rights_provenance/` | Python implementation: canonical JSON (RFC 8785-compatible), SHA-256 content identities, manifest/evidence-record construction, structural validation, graph integrity, policy evaluation mirroring the MNCS core, SPDX 2.3 import/export. |
| CLI | `mncs-rp` | `init`, `validate`, `identity`, `graph`, `attest`, `export-spdx`, `evidence verify`, `lineage verify`, `promotion evaluate`. Structured JSON output first. |
| Schemas | `schemas/v0.3/`, `schemas/v0.2/` | Canonical JSON Schemas: v0.3 manifest (additive lineage block + pressure vocabulary) and standalone lineage record; v0.2 preserved and still accepted. Builders emit 0.2.0 for lineage-free manifests (Forge / `mncs-validator-rs` keep working unchanged) and bump to 0.3.0 only when lineage is attached. Migrate with `scripts/migrate_02_to_03.py` (bumps version, invents nothing). |
| Specs | `specs/` | `distributed-pressure.md` (normative v0.3 role) and `policy-core.md` (the encoding contract) — describing what is implemented. |
| Dogfood manifests | `dogfood/` | Real manifests over real files at real commits in real MNCS repositories, generated by `scripts/dogfood_generate.py`. |
| End-to-end demo | `examples/end-to-end/run_demo.sh` | Fabric executes → emits evidence → Forge scans licenses → manifest binds both → Rust validator evaluates → Commons retains → SPDX exports. |

## Core rule

> **Uncertainty is a valid state.** Missing evidence is representable without
> fabrication; `unknown`, `unresolved`, and `insufficient-evidence` appear in
> every vocabulary where they can truthfully occur.

## Origin classifications

v0.1 vocabulary unchanged: `human-authored`, `human-ai-assisted`,
`human-directed-machine-generated`, `autonomous-machine-generated`,
`mixed-machine-origin`, `third-party-derived`,
`generated-from-licensed-source`, `generated-from-public-domain-source`,
`origin-uncertain`.

These describe **origin evidence**, not ownership or copyrightability.

## How the family uses it

- **mncs-fabric** emits standalone content-addressed evidence records from
  executions (`mncs-fabric provenance emit`). Process observations only;
  origin proposals must be caller-supplied and stay attributed claims.
- **mncs-forge-mcp** validates v0.2/v0.1 manifests (`observe/advisory/enforced`
  modes) and scans project license declarations into confidence-ranked
  evidence records (`rights.license-evidence.scan` / MCP tool
  `mncs_forge_license_evidence_scan`). Unknown license state is explicit.
- **mncs-validator-rs** enforces canonical release policy independently
  offline (`mncs-rs rights-validate`), pinned to this repository's golden
  vectors. Outcomes: `pass`, `pass-with-findings`, `review-required`,
  `blocked`, `invalid` — never a legal warranty.
- **MNCS-Commons** retains findings via `adapters/rights.py`: inert
  Observations with explicit UNKNOWN statuses; historical material stays
  historical through standard lifecycle/supersession semantics.
- **mncs-control-mcp** carries rights context across agent handoffs as
  producer references (`rights_evidence` relation).
- **mncs-harness** projects actor provenance into manifest participants with
  stable identity references (`to_rights_participant`).

## Distributed development pressure (six-repository coordination)

v0.3 makes rights/provenance a first-class participant in the coordinated
pressure workflow (MNCDS + Commons + Forge + mncs-language + MNCS + this
repository). See `specs/distributed-pressure.md` (normative role) and
`docs/distributed-pressure-provenance.md` (contributor guide with a worked
cross-repository example).

```bash
python3 language/tools/gen_pressure_corpus.py  # regenerate pressure corpora + vectors
bash language/run_backend_tests.sh             # multi-backend execution checks
python3 -m pytest tests/test_pressure_provenance.py
mncs-rp lineage verify dogfood/distributed-pressure-changeset.json
mncs-rp promotion evaluate dogfood/distributed-pressure-changeset.json
python3 scripts/dogfood_pressure.py            # regenerate six-PR dogfood lineage
python3 scripts/migrate_02_to_03.py RIGHTS.json
```

The dogfood lineage record binds the five sibling pressure PRs
(MNCDS #7, Commons #32, Forge #74, mncs-language #104, MNCS #71) plus this
work into one reconstructable ChangeSet, with explicit UNKNOWNs wherever
evidence is genuinely absent.

## Policy evaluation

Gate semantics live in `language/rights_policy.mncs`; see
`specs/policy-core.md` for the encoding contract, gate table, enforcement
ceilings, and outcome derivation. Host implementations are tested against
golden vectors generated from that core:

```bash
python3 language/tools/gen_corpus.py        # regenerate corpora + vectors
bash language/run_backend_tests.sh          # multi-backend execution checks
python3 -m pytest tests/test_policy_golden.py
(cd ../mncs-validator-rs && cargo test --test rights)
```

## Validate the examples

```bash
python3 -m pip install -e ".[dev]"
python3 -m pytest tests -q
python scripts/validate_examples.py         # legacy v0.1 schema examples
python scripts/dogfood_generate.py && python3 -c "
from pathlib import Path
import subprocess, sys
for path in sorted(Path('dogfood').glob('*.json')):
    result = subprocess.run(['mncs-rp', 'validate', str(path), '--findings-are-not-failures'])
    if result.returncode not in (0, 4):
        sys.exit(f'{path}: validation failed')"
```

## Maturity and limitations

- The MNCS-language core runs its full corpus on the `research-bytecode`
  backend and its evaluate/lattice corpora on `portable-wasm`; scalar backends
  refuse records at present. Backend gaps and other language findings are
  documented precisely in `docs/language-findings.md`.
- Attestation signatures have an extension point (ed25519 detached block);
  signature *verification* lives with consumers' trust policy (see
  `mncs-validator-rs attestation/trust`), not in this format layer.
- Passing policy means project evidence requirements were met. It is not a
  warranty of title or non-infringement.
